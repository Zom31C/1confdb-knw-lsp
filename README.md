# 1confdb-knw-lsp

Единый MCP-сервер знаний по конфигурации 1С:Предприятие 8 для LLM:
**метаданные, код и запросы** из бинарного `.cf` — без платформы 1С и EDT.

Сервер объединяет в одном MCP-соединении два инструмента:

- **confdb** (Python) — база знаний SQLite по конфигурации: объекты, реквизиты
  с типами, табличные части, модули BSL, методы, запросы СКД, валидатор языка
  запросов 1С — **19 инструментов**;
- **BSL Language Server** (форк
  [bsl-language-server](https://github.com/1c-syntax/bsl-language-server)) —
  AST-анализ кода конфигурации: символы, ссылки, иерархия вызовов, типы,
  диагностики — **10 инструментов `bsl_*`**. Поднимается как дочерний процесс,
  LLM-клиенту нужен один сервер.

Алгоритм распаковки `.cf` портирован из проекта
[v8unpack](https://github.com/saby-integration/v8unpack) (MIT, см. NOTICE.md) —
только в одну сторону: распаковка и разбор, без обратной сборки.

## Установка

Требования: Windows, Python 3.9+ (только стандартная библиотека), JDK 21
(для инструментов `bsl_*`), клон форка
[Zom31C/bsl-language-server-confdb](https://github.com/Zom31C/bsl-language-server-confdb).

```bat
:: 1. Виртуальное окружение + пакет; при отсутствии JDK 21 предложит
::    установить его через winget
setup.bat

:: 2. Собрать jar BSL Language Server из форка (ветка confdb-metadata-source);
::    путь к форку — аргументом или ..\..\..\bsl-language-server-confdb
build-lsp-jar.bat D:\path\to\bsl-language-server-confdb
```

`bin\bsl-language-server.jar` в репозиторий не входит (~143 МБ) — он и есть
результат шага 2.

## Подготовка конфигурации (однократно)

```bat
:: извлечь .cf в базу знаний + дамп файлов (модули .bsl)
confdb.bat extract config.cf --db out.db --dump workspace

:: подготовить дамп для BSL Language Server (UTF-8 без BOM, переводы строк LF)
confdb.bat prep-lsp workspace

:: проверить запросы в модулях и сохранить нарушения в таблицу query_violation
:: (их подсветит диагностика ConfdbQueryValidation в bsl_analyze_file)
confdb.bat check-queries out.db
```

## Запуск MCP-сервера

```bat
:: stdio (основной режим для MCP-клиентов)
1confdb-knw.bat out.db --lsp-workspace workspace

:: HTTP для доступа по сети / через SSH-туннель
1confdb-knw.bat out.db --port 8765 --lsp-workspace workspace
```

База по аргументу необязательна: без неё берётся `last_db` из
`~/.confdb/config.json`, затем автопоиск `*.db`/`*.sqlite` (текущий каталог,
`db/`, `_out/`). Workspace (`--lsp-workspace`) запоминается в конфиге
(ключ `lsp_workspace`) — при следующих запусках достаточно
`1confdb-knw.bat out.db`. Без jar/java сервер продолжает работать в режиме
«только confdb» (без `bsl_*`).

Конфигурация MCP-клиента (Claude Code и др.):

```json
{
  "mcpServers": {
    "1confdb-knw": {
      "command": "D:\\path\\to\\1confdb-knw-lsp\\1confdb-knw.bat",
      "args": ["D:\\path\\to\\out.db"]
    }
  }
}
```

По сети — через SSH-туннель и URL-режим:

```bat
ssh -L 8765:127.0.0.1:8765 user@host
```

```json
{ "mcpServers": { "1confdb-knw": { "url": "http://127.0.0.1:8765/mcp" } } }
```

По умолчанию слушает `127.0.0.1` (база read-only, аутентификации нет);
`--host 0.0.0.0` открывает порт наружу — только в доверенной сети.

## Инструменты

### confdb — метаданные и код из базы знаний

| Инструмент | Назначение |
|---|---|
| `find_objects` | поиск объектов по имени/типу (маска опциональна — можно листать тип целиком) |
| `object_card` | «паспорт» объекта: реквизиты с типами, табличные части, модули, формы и команды, значения перечислений, предопределённые элементы, ссылки вперёд/назад; у регистров измерения, ресурсы и реквизиты отдельными группами плюс периодичность и режим записи |
| `object_tree` | дерево объектов «как в конфигураторе» |
| `find_field` | обратный поиск: у каких объектов есть поле |
| `refs_of` | связи по типам реквизитов (impact analysis) |
| `module_outline` | оглавление модуля без тел методов; пагинация `offset`/`limit` |
| `get_method` | исходник процедуры/функции; длинные методы листаются (`offset`/`limit`) — ничего не обрезается молча |
| `find_method_context` | окно строк вокруг нужного вызова с номерами строк модуля и маркерами точки вставки — дешевле `get_method` на больших методах |
| `method_dependencies` | что нужно методу для работы: общие модули и их экспортные методы, метаданные, таблицы и поля его запросов, параметры; если рядом открыта основная конфигурация, зависимости расширения/обработки находятся в ней, а ответ называет базу-источник |
| `method_result_schema` | из чего состоит возвращаемая методом таблица значений/структура (эвристика по тексту) |
| `find_methods` | поиск методов по фрагменту имени/сигнатуры/описания (маска опциональна); параметр `text` ищет подстроку **внутри тел** методов и выдаёт номер строки модуля — так находятся все обращения к объекту без полнотекстового `sql` |
| `skd_of` / `find_skd` | запросы СКД объекта / по тексту |
| `check_query` | валидация запроса 1С: синтаксис + метаданные |
| `schema` | справочник схемы базы (таблицы/колонки/число строк) — вызывать перед `sql` |
| `sql` | только SELECT, для непокрытых случаев |
| `compare_object` | различия одного объекта в двух открытых базах (`db_left`/`db_right`): реквизиты и типы, табличные части, группы полей регистра, формы, модули, методы, запросы СКД |
| `extension_diff` | что делает расширение относительно основной конфигурации (`extension_db`/`base_db`): новые и заимствованные объекты, его методы и какой штатный метод они замещают (`&Вместо`) или обходят (`&После`/`&Перед`), добавленные реквизиты, внешние зависимости |
| `configuration_info` | какая конфигурация и какой релиз в базе: тип загруженного файла (`.cf` конфигурация, `.cfe` расширение, `.epf` внешняя обработка, `.erf` внешний отчёт), имя, версия, режим совместимости (у обработок и отчётов его нет, расширение наследует режим основной конфигурации), исходный файл и дата выгрузки |

Пути модулей понимаются в любой форме: `Документ.Х` + `code_name='mgr'`,
`Документ.Х.mgr`, `Документ.Х.obj.bsl`, `Документ.Х.МодульМенеджера`,
`Document/Х/Document.mgr.bsl`.

**Идентификатор базы в ответах:** каждый ответ инструмента данных начинается
с заголовка `=== база <алиас> (<путь>) ===`, идентифицирующего источник данных.
Это позволяет сравнивать конфигурации (типовая vs доработанная, основная vs
расширение) и понимать, в какой базе находится метод или объект. При открытии
нескольких баз используйте параметр `db='алиас'` для выбора конкретной базы
или `db='*'` для запроса ко всем базам сразу (ответ придёт секциями по базам).

### bsl_* — анализ кода (BSL Language Server)

`bsl_analyze_file` (диагностики и метрики, включая `ConfdbQueryValidation` —
ошибки запросов из `check-queries`), `bsl_document_symbols` (есть компактный
режим `outline: true`), `bsl_find_references`, `bsl_call_hierarchy`,
`bsl_hover`, `bsl_definition`, `bsl_type_info`, `bsl_type_at_position`,
`bsl_global_member_info`, `bsl_global_member_search`.

Файлы для `bsl_*` задаются путями относительно корня дампа
(`Catalog/Товары/Товары.obj.bsl`, `CommonModule/Имя/CommonModule.obj.bsl`);
метаданные для анализа берутся из той же базы confdb
(`.bsl-language-server.json` с `confdbDatabase` создаётся в workspace
автоматически). Первый вызов `bsl_*` сразу после старта может попасть на
индексацию дампа (~10–30 с) — повторите.

Инструкции протокола (`initialize.instructions`) и описания инструментов
содержат справочник по схеме базы, глоссарий 1С и рекомендуемый рабочий
процесс; в `CLAUDE.md` — расширенное руководство для LLM.

## Проверка запросов СКД

`confdb check <база>` прогоняет запросы таблицы `skd_query` через встроенный
разборщик языка запросов 1С (`query_lang.py`):

- синтаксис: ПОМЕСТИТЬ/УНИЧТОЖИТЬ, ОБЪЕДИНИТЬ [ВСЕ], соединения (включая
  вложенные и перечислением), вложенные запросы, ВЫБОР/ВЫРАЗИТЬ, виртуальные
  таблицы с аргументами, параметры `&…`, необязательные области СКД `{…}`,
  ДЛЯ ИЗМЕНЕНИЯ, ГРУППИРУЮЩИЕ НАБОРЫ, В ИЕРАРХИИ, ИТОГИ, АВТОУПОРЯДОЧИВАНИЕ;
- семантика по метаданным: существование таблиц и полей первого уровня,
  цепочки разыменования ссылок через `attribute_ref`.

`confdb check-queries <база>` делает то же для текстов запросов в модулях и
сохраняет нарушения в `query_violation` (path + позиция литерала в файле) —
их подсвечивает `bsl_analyze_file`.

## Опции `extract`

- `--db FILE` — записать результат в SQLite;
- `--dump DIR` — сохранить распакованное дерево файлов
  (нужен хотя бы один из `--db`/`--dump`);
- `--temp-dir DIR`, `--keep-temp` — рабочий каталог стадий 0–1;
- `--prefix STR` — снять префикс с имён объектов;
- `--store-blobs` — хранить бинарные файлы в БД как BLOB;
- `--workers N` — число процессов (по умолчанию — результат `confdb bench`).

Стадии конвейера (повторяют v8unpack, только распаковка):
0 — чтение внешних V8-контейнеров (32/64-бит); 1 — inflate + рекурсивные
вложенные контейнеры; 3 — декодирование метаданных: скобкофайлы `{}` → JSON,
тексты модулей → `.bsl`.

## Бенчмарк и автонастройка

`confdb bench <file>` прогоняет нелинейный сэмпл объектов через стадию 3 и
запись БД при 1/2/4/8/CPU процессах; лучшее число сохраняется в
`~/.confdb/config.json` и подставляется по умолчанию в `extract`.

## Схема базы данных

- `source` — исходный файл и корневой объект;
- `meta_object` — объекты метаданных: `path`, `type`/`type_ru`, `name`, `uuid`,
  `header_json` (полный заголовок), `parent_id` + `ord` (иерария как в
  конфигураторе);
- `meta_attribute` — реквизиты: `type_str` (`Строка(50)`, `Ссылка: Catalog/Х`,
  `ОпределяемыйТип: …`, составные через ` | `), `tabular` — имя табличной части;
- `attribute_ref` — связи реквизитов с объектами (impact analysis join'ами);
- `meta_tabular` — табличные части; `enum_value` — значения перечислений;
  `predefined` — предопределённые элементы; `common_target` — привязка общих
  реквизитов;
- `module` — паспорт модуля (`code_name`, `context`) и его сокращённое тело
  (без тел методов); `method` — процедуры/функции: сигнатура, `is_export`,
  директивы `&НаКлиенте/…`, описание, `line_start/line_end`, тело;
- `skd_query` — запросы из макетов СКД; `query_violation` — нарушения запросов
  в модулях (пишет `check-queries`);
- `subsystem_content` — состав подсистем;
- `file` — карта файлов дампа: путь, объект, тип (включая `.bsl`-модули).

Примеры запросов:

```sql
-- реквизиты справочника с типами
SELECT a.name, a.type_str
FROM meta_attribute a JOIN meta_object o ON o.id = a.object_id
WHERE o.path = 'Catalog/Контрагенты' ORDER BY a.ord;

-- тело конкретного метода
SELECT mt.body FROM method mt JOIN module m ON m.id = mt.module_id
JOIN meta_object o ON o.id = m.object_id
WHERE o.path = 'Document/Заказ' AND m.code_name = 'obj'
  AND mt.name = 'ПриПроведении';
```

## Состав дистрибутива

- `src/confdb/v8` — ядро распаковки (контейнеры 1С, inflate, скобкофайлы);
- `src/confdb/db` — схема SQLite и запись;
- `src/confdb/extract.py` — конвейер стадий; `bench.py` — бенчмарк;
- `src/confdb/query_lang.py` — разбор и контроль языка запросов 1С;
- `src/confdb/query_check.py` — `check-queries` (запросы в модулях);
- `src/confdb/lsp_prep.py` — `prep-lsp` (дамп → LF без BOM);
- `src/confdb/bsl_analyzer.py` — лексический анализ BSL для `method_dependencies`
  и `method_result_schema` (синтаксис модулей не проверяет — это делает BSL LS);
- `src/confdb/compare.py` — снимки объектов и diff между базами
  (`compare_object`, `extension_diff`);
- `src/confdb/header_props.py` — разбор `header_json`: версия конфигурации,
  измерения/ресурсы/реквизиты регистров;
- `src/confdb/mcp_server.py` — MCP-сервер (19 инструментов confdb + шлюз);
- `src/confdb/mcp_bsl_proxy.py` — шлюз к BSL Language Server (stdio);
- `src/confdb/tui.py` — текстовый интерфейс (`confdb-ui.bat`);
- `tests` — тесты (`test.bat`).
